# Data

> **What you get from this page:** what each data file holds, the field definitions, and how the published numbers were produced from the raw benchmark exports.

## The answer first

- **Client results** for every configuration and load are in `<node>/<config>.points.json`, rebuilt from the AIPerf exports with warm-up requests excluded.
- **Every request** behind those points is in `requests/<node>/<config>.csv.gz` (286,453 rows), so SLO-ok, percentiles and goodput can be recomputed for any SLO.
- **Derived tables** (rankings, frontiers, every point) are in `derived/`, generated by `scripts/derive.py`.
- **Server-side measurements** (KV capacity, NIXL transfers, prefix hits, preemptions, autoscaling timelines) are in `server-metrics.json` and the two `stage-timings.md` files; their raw scrapes are not published.

## Evidence: files and fields

| Path | Contents |
|---|---|
| `configs.json` | One entry per configuration: node, GPU count, family (agg, pd, knob, prefix, agentic), human label, router, KV dtype, block size, GPU split, notes |
| `h100/*.points.json`, `a100/*.points.json` | Client results, one record per (shape, concurrency) |
| `requests/<node>/*.csv.gz` | Per-request records: `shape, c, phase (m = measured, w = warm-up), ttft_ms, itl_ms, isl, osl, e2e_ms` |
| `h100/stage-timings.md`, `a100/stage-timings.md` | Mean time per request in each server stage, from vLLM histograms (`scripts/layers.py`) |
| `a100/routing-runs.json` | The A100 router comparison: one record per run, client percentiles recomputed from per-request records, engine hit rate, preemptions, per-pod request counts (sorted, pod names removed) |
| `server-metrics.json` | Values measured from vLLM, router, UCX, Nsight Systems and planner signals, each with how it was measured |
| `derived/goodput.json`, `derived/frontiers.json`, `derived/TABLES.md` | Output of `scripts/derive.py` |

**Points fields**

| Field | Meaning |
|---|---|
| `config`, `node`, `gpus`, `shape`, `c` | Configuration, node, GPUs the layout uses (all prefill and decode GPUs), workload shape, concurrency |
| `n_measured`, `n_warmup` | Requests in the measured phase and in the warm-up (agentic points have no warm-up) |
| `req_s`, `out_tok_s`, `out_tok_s_gpu` | AIPerf request and output-token throughput for the measured phase; per GPU = / `gpus` |
| `eff_conc` | req/s x mean request latency / c |
| `ttft_p50_ms`, `ttft_p90_ms`, `ttft_p99_ms` | Client TTFT percentiles over measured requests (linear interpolation) |
| `itl_p50_ms`, `itl_p90_ms`, `itl_p99_ms` | Percentiles of per-request mean ITL over measured requests |
| `tok_s_user_p90` | 1000 / `itl_p90_ms` |
| `slo_ok` | Share of measured requests with TTFT <= 2,000 ms and mean ITL <= 50 ms |
| `slo_ok_incl_warmup` | The same share with warm-up requests included (kept for traceability) |
| `goodput_req_s_gpu` | `req_s` x `slo_ok` / `gpus` |

**How the files were produced.** `scripts/build_points.py` read each run directory (AIPerf `profile_export_aiperf.json` plus the per-request `profile_export.jsonl`), and the results were checked against the earlier analysis of the same runs: all 142 original points reproduce exactly for throughput, TTFT p50 / p90 / p99, ITL p50 / p99 and effective concurrency, and for SLO-ok when warm-up is included. ITL p90 and the agentic c256 points (H100) and all A100 agentic points were added from the same per-request records.

## What to do with it

- Re-rank for your own target: `SLO_TTFT_MS=1000 SLO_ITL_MS=30 MIN_SLO_OK=0.95 python3 scripts/derive.py` recomputes SLO-ok and goodput from `requests/`.
- Read a points record together with its `slo_ok` and `eff_conc`: a high-throughput point with low SLO-ok or eff below 0.9 is not an operating point.
- Never place an H100 record next to an A100 record: different GPUs, GPU counts and prefill budgets.
